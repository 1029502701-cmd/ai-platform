# v1.8.0 - Notification Center Foundation Release Date: 2026-07-28

## Overview

Platform-008 introduces the unified Notification Center Foundation, providing a centralized notification delivery system for all business modules, Plugins, Workflows, and Billing components. All future notification operations must route through NotificationService.

## Migration

Added new migration drizzle/0042_notification_center.sql with 5 tables:

1. **notification_templates** - Stores reusable notification templates with variable support and versioning
2. **notifications** - Core notification storage with status tracking and delivery counts
3. **notification_logs** - Delivery attempt logs for each notification per channel
4. **notification_preferences** - User notification preferences per channel and notification type
5. **notification_channels** - Pre-seeded channel configurations (system, email, wechat, sms, webhook, push)

## Repository Pattern

All repositories implement tenant-scoped queries via 	enantId parameter, ensuring strict tenant isolation:

- **NotificationRepository**: CRUD for notifications, delivery tracking, scheduled notification fetch
- **NotificationTemplateRepository**: Template CRUD with version increment support
- **NotificationPreferenceRepository**: User preference management per channel
- **NotificationLogRepository**: Delivery log persistence and retrieval

## Service Interface

NotificationService provides the unified notification API:

| Method | Description |
|--------|-------------|
| send(request) | Send a single notification immediately |
| roadcast(request) | Send to multiple users (admin/subscription use case) |
| schedule(req, options) | Schedule with delayMs or at(timestamp) |
| cancel(id) | Cancel a pending notification |
| 
etry(id) | Retry a failed notification |
| preview(templateId, vars) | Render template with variables |
| getHistory(userId, opts) | Get notification history with delivery logs |
| markRead(id) | Mark notification as read |

All methods emit EventBus events: 
otification.created, 
otification.sent, 
otification.failed, 
otification.retry, 
otification.read, 
otification.deleted.

## Provider System

Providers implement the NotificationProvider interface with send() and preview() methods:

- **MockProvider** - Default (logs to console, always succeeds)
- **EmailProvider** - Placeholder for SMTP/email service integration
- **SMSProvider** - Placeholder for SMS gateway integration
- **WebhookProvider** - Placeholder for webhook delivery
- **WechatProvider** - Future placeholder for WeChat Work/Official Account
- **PushProvider** - Future placeholder for push notifications

## Channel Support

Notification channels determine delivery target and rendering behavior:

- **System** - In-app notification, renders content directly
- **Email** - Email subject/body rendering with template variables
- **WeChat** - WeChat message format rendering
- **SMS** - SMS-length constrained rendering (160 char limit)
- **Webhook** - JSON payload building for webhook endpoints
- **Push** - Push notification payload construction

## Template System

Template system supports variable substitution with 5 built-in variables:

- {{user}} - User data object
- {{plugin}} - Plugin reference data
- {{workflow}} - Workflow execution context
- {{time}} - Current timestamp
- {{order}} - Order/reference data

Template versioning allows tracking changes to templates over time.

## Event System

EventBus emits the following events:

- 
otification.created - When notification is created
- 
otification.sent - When notification is successfully delivered
- 
otification.failed - When notification delivery fails
- 
otification.retry - When notification is retried
- 
otification.read - When notification is marked read
- 
otification.deleted - When notification is deleted

All events carry { event, payload, timestamp } structure.

## Scheduler

Scheduler supports:

- **Immediate** (default) - Send immediately
- **Delayed** (delayMs) - Send after N milliseconds
- **Scheduled** (t ISO timestamp) - Send at specific time
- **Recurring** (cron) - Future extension point (reserved)

Retry policy configurable per notification: maxRetries, delayMs.

## Queue Integration

Uses existing QueueAdapter pattern - no new queue implementation per requirement. All notifications can be queued for background processing.

## Platform Integration

### Identity Integration
- Reads user_id from request context
- Checks notification_preferences for user-specific channel enable/disable
- Future extension: read user language and timezone for localized notifications

### Permission Integration
- All repository queries scoped by 	enant_id
- Admin services can access broader notification sets
- Normal users only access their own notifications

### Billing Integration
- Template types include payment-related categories (transactional, alert)
- NotificationType field supports payment-success, refund, subscription-expiration values

### Storage Integration
- Payload supports arbitrary metadata for attachments, images, files
- Notification model includes metadata storage

### Workflow Integration
- Workflow Engine can call NotificationService.send()
- Workflow can listen to notification events for failure handling
- Failed notifications auto-retry per retry policy

### Plugin SDK Integration
- NotificationService exported for plugin consumption
- Plugins can send, broadcast, and schedule notifications

### Queue Integration
- NotificationQueue adapter delegates to existing queue system
